# 全部仓库动态 → 多个 QQ 通知群

当前通知群：**123456789**。支持添加多个通知群，每个群可以使用不同的发送机器人，分别绑定、启停、测试或移除。不需要逐个仓库添加推送规则。

## 连接一次 GitHub

点击「使用 Token 连接 GitHub」，创建一个专用于机器人的 [GitHub fine-grained Token](https://github.com/settings/personal-access-tokens/new)。资源所有者选择自己的账号，Repository access 选择 All repositories。

建议仓库权限：Metadata、Contents、Issues、Pull requests、Actions、Discussions 读取；自动创建实时通知回调还需要 Webhooks 读写。只有 Token 可访问的仓库会被接入；组织仓库可能需要组织管理员审批。不把操作系统中其它工具的 Token 自动复制到机器人。

Token 输入管理台后由后端验证账号并加密保存，接口不回显明文。不需要在聊天里发送 Token。现有 OAuth App 授权入口仍可使用，但 Token 方式不依赖 OAuth App 和回调域名。

## 绑定通知群

点击「添加通知群」，选择发送机器人，填写实际 QQ 群号，点击「保存并绑定」。现有单群配置升级后自动保留，无需重新绑定原来的群。

- QQ 官方机器人：每个群各有一个绑定口令，把机器人加到对应群，在群里 @ 机器人并发送该群的口令。10 分钟内有效且只能使用一次；生成第二个群的口令不会使第一个群的口令失效。收到「绑定成功」后，后台会显示已绑定。该方式关联群 OpenID，真实 QQ 群号由你填写，平台无法自行核实。消息列表、群聊管理、推送规则和记录展示填写的 QQ 群号，内部发送映射保持不变；未知的官方群会显示「未标注群号」。

官方机器人必须实际收到群事件：本机未公开接收地址时可以使用账号的 WebSocket 回调方式；服务器使用 Webhook 回调时需在 QQ 开放平台配置 HTTPS 地址。主动通知还受腾讯平台的权限、群主动消息开关和额度限制。

**两处设置必须一致**：后台「QQ 账号管理」选择 WebSocket 后，还要到 QQ 开放平台的该机器人「开发设置 → 事件订阅与回调」，选择 WebSocket 并点击保存。本地账号设置不会自动修改 QQ 开放平台。平台若仍选 Webhook，会继续向原回调地址投递；此时本地网关即使显示已连接，也收不到群消息。切换后重新发送绑定口令，切换前的消息不会自动补送。

在对应群的卡片点击「检查群权限」，后台会读取 QQ 官方接口的 `allow_proactive_msg`，显示主动推送是否已允许和检查时间。若是「未允许」，请由群主或管理员在 QQ 客户端打开这个群内机器人的资料或管理设置，开启「允许主动发送／主动推送」，然后再次检查。该授权属于 QQ 群，本地账号的主动发送开关不能代为授权。部分机器人可能没有群状态查询接口的访问权限，此时显示查询失败，不会把未知状态当成关闭。

**官方 QQ 机器人支持群主动推送**。绑定成功只证明可以收到并回复群消息，不证明该群已经允许主动推送。错误 `40034105` 表示主动消息无权限，应先检查群内授权。2026-11-13 本地实测：群 123456789 的 `allow_proactive_msg=false` 时，版本通知被拒绝；群内开启后接口返回 `true`，包括版本、分支、PR 和评论在内的 23 条积压通知全部补发成功，并取得 QQ 消息 ID。

在对应群的卡片点击「测试主动通知」，到该群检查。测试会绕过最近一次 @ 的被动回复上下文，使用独立主动消息验证自动推送；QQ 未返回消息 ID 时不会计为成功。此操作不代表 GitHub 已授权或已发生真实事件。

添加第二个群不会覆盖第一个群。每个已绑定并启用的群会获得独立的仓库推送规则，同一动态会分别投递和记录结果。停用、修改或移除一个群，只影响这个目标；移除保留既有投递历史并作废该群未使用的绑定口令。消息、群聊与推送筛选仍以账号和内部群映射共同定位，避免不同机器人恰好有相同映射 ID 时混淆。

## 全部项目自动接入

启用通知并保存后，调度器在后台逐页发现已连接账号**拥有**的所有授权可见仓库，自动附加所有已绑定、启用的通知群和事件选择。首次只建立历史基线；约每分钟再次同步仓库清单。协作但不属于该账号的仓库、其他平台用户管理的仓库不自动接管。

完整清单中不再可见的自动接入仓库会标记为不可访问，退出当前列表与仪表盘计数，并停止轮询及推送规则；版本、事件与投递历史仍保留。不可访问可能来自删除、转移或 Token 授权变化，不等于已确认永久删除。列表读取失败或分页未完成时不会根据残缺列表移除仓库；恢复可见后可以重新接入。已安装实时 Webhook 时也处理仓库删除/转移事件。仪表盘和仓库表在页面可见时每 10 秒更新，切回页面会刷新，不承诺零延迟。

新安装的后台在首次登录时提供教学入口，左侧「新手指引与文档」包含五步设置流程和可搜索的操作说明。每一步根据真实状态显示检查结果，阅读到下一步不会被当作配置已成功。邮件设置见 [首次使用与失败邮件](FIRST_USE_AND_EMAIL.md)。

支持提交、版本发布、分支/标签增删、PR、Issue、评论、审核、Star、Fork、Wiki、协作者、讨论和 Actions 完成事件。消息包含仓库、操作者、动作、简要内容和详情地址；一次推送超过 8 个提交只展示前 8 个。不同事件的详情取决于 GitHub 实际提供的数据，缺失内容不会编造。

## Markdown 卡片样式

「推送规则」表单可以开启 **Markdown 卡片**：代码推送等动态和版本发布通知都会以 QQ 官方机器人原生 Markdown 深色卡片投递（标题、提交内容与变化文件代码块、统计信息、更新内容），底部附带跳转按钮。轮询路径会借用 compare 接口的数据补充新增/减少行数统计。

- 原生 Markdown 与自定义按钮需要机器人在 QQ 开放平台拥有对应消息权限；未开通时接口会拒绝。
- 卡片发送失败时**自动降级为纯文本重发**，并写入一条 WARNING 日志，推送不会因此中断；「推送记录」中的内容始终是纯文本。
- 版本发布卡片的数据随推送记录持久化：规则开启卡片后，失败重试与手动重发也以卡片样式投递。
- 卡片与文本版信息一致：规则的「附带更新日志」「附带下载地址」「AI 摘要」开关同样作用于卡片；消息模板只影响纯文本版，卡片样式固定。

页面显示同步状态、接入数、失败仓库、授权/机器人/群绑定警告；每个群显示最近 7 天成功、失败、待发送的数量和投递错误（统计最多最近 1000 条记录）。检测到主动消息无权限时，会明确显示「群投递受限」。「推送记录」显示投递内容与错误，可手动重试。后台每分钟重试失败通知，默认最多 3 次；账号离线时暂缓，不消耗重试次数或覆盖原始错误。停止通知或改变目标后，旧失败通知会被取消。进程中断后超过 5 分钟的待发送记录会尝试恢复；发送成功但确认落库前中断仍可能重复，不能保证跨 QQ 与数据库的恰好一次投递。

## 实时通知与轮询的区别

- 本地或无公网 HTTPS：保持「自动为仓库配置实时 Webhook」关闭，采用轮询。GitHub Events API 官方注明可能延迟 30 秒至 6 小时，仅保留最近 30 天、最多 300 条，并且并非所有 Webhook 事件都会出现在活动列表中，因此**不能保证所有动态即时送达**。Actions 和讨论评论等完整事件需要 Webhook。轮询请求遵守 GitHub 的 X-Poll-Interval；仓库较多时自动加长间隔，为同步等操作保留 API 配额。页面显示实际间隔。
- 服务器公网 HTTPS 就绪：设置 `.env` 的 `PUBLIC_BASE_URL=https://你的域名`，为 Token 授予 Webhooks 读写，勾选自动 Webhook 后保存。后台仅创建/更新 URL 与本站精确一致的回调，不覆盖其它集成；每仓库使用随机 Secret 并验证 HMAC。失败的仓库会列出来，后续同步重试。取消勾选后不再自动修改 GitHub，已安装的回调仍会进入后台并按当前通知规则处理；如要移除回调，可在 GitHub 仓库 Settings → Webhooks 中删除本站地址。

Webhook 重投通过事件/投递标识去重；Webhook 与轮询对于相同分支与 before/after 提交的代码推送也共享去重键。GitHub 的两种通道不提供统一事件 ID，部分分支、Star 等事件经两种通道到达时可能各有一条通知。

参考：[GitHub Events API](https://docs.github.com/en/rest/activity/events)、[仓库 Webhook API](https://docs.github.com/en/rest/repos/webhooks)、[QQ 官方消息收发概述](https://bot.q.qq.com/wiki/develop/api-v2/server-inter/message/overview.html)。QQ 平台规则应以当前官网文档与实际接口结果为准，旧的 GitHub 文档快照可能已经过时。

## 上传服务器

准备不含本地凭据和数据库的源码包：

```powershell
python scripts/package_server.py
```

把 `.downloads/qbot-server.zip` 上传 Linux 服务器并解压，安装 Docker Engine、Compose v2 和 Python 3。在解压目录运行：

```bash
python3 scripts/prepare_server.py --public-url https://你的域名
docker compose up -d --build
docker compose ps
curl -f http://127.0.0.1:8080/api/system/health
```

初始用户名 admin，随机初始密码在服务器 `.env` 的 ADMIN_PASSWORD 中。脚本拒绝覆盖已有 `.env`，不会在终端输出密码。默认仅绑定 127.0.0.1:8080，请用 Nginx/Caddy 等配置 HTTPS 反向代理及访问控制。GitHub 与 QQ 的回调需要允许访问对应 `/api/webhook/github/...` 和 `/api/qqbot/webhook/...` 路径。

该源码包采用全新的 PostgreSQL 数据卷，因此服务器首次部署需要在页面重新填写 QQ 凭据、连接 Token 和绑定群。**本地 SQLite 数据不会自动变成 PostgreSQL 数据**。如果要迁移已有配置，请先设计并验证数据库迁移方案，且保留原 SECRET_KEY；更换 SECRET_KEY 会使原有加密 Token 与 QQ AppSecret 无法解密。不要直接把本地 backend/.env 复制成服务器配置，它含本机路径和开发开关。

Compose 默认在持有机器人连接的 backend 中开启调度。动态、多群与邮件迁移 `0008_github_activity` / `0009_notification_targets` / `0010_guides_email_sync` 会保留已有版本通知及规则，新增仓库可访问状态与持久邮件队列。已有库升级前先备份；包含动态或邮件记录时降级会拒绝丢弃这些数据。

当前本地验证与服务器部署是两件事：真实 GitHub → 公网 Webhook → QQ 群投递，需要实际授权、回调与群权限共同验收。
