# v1.6 更新发现兼容性与旧版修复指南

## 检查器与浏览器的兼容边界

继续使用 `UPDATE_REPOSITORY=yuchen0x1/AI-QQ-Bot`、`/api/system/update` 和 GitHub 正式 Release。原有 JSON 字段与资产字段保留；新增检查时间、最近成功时间、缓存年龄、过期标志、下次重试时间和重试等待秒数。旧客户端可以忽略新增字段。

- `stable` 拒绝 Draft、预发布标志及带预发布段的版本号。
- `beta` 只接受非 Draft 的有效预发布版本，按 SemVer 选择最高版本；不以最新稳定版代替 Beta。
- 远程版本低于当前版本时返回诊断，不提示降级。
- 按更新源、仓库、通道和凭据指纹缓存 60 秒，合并并发检查，并发送 `If-None-Match`。指纹不包含明文凭据。
- `304` 代表成功重新验证；网络错误、`403`、`429` 不更新最近成功时间。失败后保留最近成功结果并标记 `stale=true`、`ok=false`，管理台展示缓存诊断，并禁止用过期结果开启安装。
- 尊重 `Retry-After` 的秒数或 HTTP 日期、GitHub 额度重置时间；无有效时间时最少退避 30 秒。手动检查可绕过成功缓存，但不能绕过错误退避。
- 携带 GitHub Token 的检查请求不跟随重定向；仅遇到 Token 的 `401` 才匿名重试。`403/429` 不通过连续匿名重试规避限流。
- `UPDATE_CHECK_INTERVAL_MINUTES=0` 关闭浏览器自动提醒和后续定时检查，手动检查保留。管理台仍须首次读取配置，才能获知关闭设置。

“稍后提醒”保存 `{version, snooze_until}`，期限为 6 小时。同一版本到期后，已经打开的页面也会恢复提醒；更高版本不受前一版本的延后影响。同一浏览器的多个标签页通过 `storage` 事件同步，重新登录后沿用尚未过期的期限。旧 `qbot_deferred_update` 没有时间戳，首次读取时迁移为一次 6 小时延后并删除旧键，不再永久隐藏。没有增加“忽略此版本”动作。

|---|---|---|---|---|---|
| v1.4.12 | `e6e7c9171ad07a26d9cbfc7b6e1439767f233fbf` | 可发现 v1.6.0 | 401，不能自行匿名重试 | 返回失败诊断 | 恢复后可发现 |

| v1.5.3 | `181c13009ad2ca7c3fa7fbd133c828ee1134a85b` | 可发现 v1.6.0 | 匿名重试后可发现 | 返回失败诊断 | 恢复后可发现 |

上表是 **18 个受控 HTTP 场景** 的结果，候选元数据与下载资产是测试数据，不是已完成正式发布的证据。发布后须再次运行 `--live`，让上述旧代码直接读取真实 GitHub Release。脚本会如实对未能发现的场景返回非零退出码，已知 v1.4.12 失效 Token 缺陷作为已验证限制单独记录。

```bash
# 先安装本项目后端依赖；本地 Git 对象中必须有三个历史标签。
python scripts/probe_legacy_updates.py --candidate-version 1.6.0 \
  --report .acceptance/legacy-updates-fixture.json

# 正式发布后：匿名、失效 Token、已有 gh 凭据的有效 Token 直查真实版本源。
python scripts/probe_legacy_updates.py --candidate-version 1.6.0 --live --use-gh-token \
  --report .acceptance/legacy-updates-live.json
```

`--use-gh-token` 只在子进程内通过现有 `gh auth token` 凭据存储读取 Token，不写入源码、磁盘报告或日志。不需要有效 Token 场景时省略该参数。

2026-11-25 发布后实测（UTC `2026-11-25T09:26:28Z`）使用三个正式标签的**未修改旧源码**直接读取真实 `v1.6.0` Release：v1.4.12、v1.5.2、v1.5.3 在有效 GitHub Token 下均发现 v1.6.0，且均读取到五项正式资产。当前出口对匿名 GitHub API 返回 `403` 且 `X-RateLimit-Remaining: 0`，所以匿名场景和依赖匿名回退的失效 Token 场景不能作为通过；v1.4.12 的失效 Token 不匿名重试仍是已知历史限制。该实测证明有效凭据路径可发现正式版本，不承诺所有网络、失效凭据或关闭轮询的旧进程都会立即提示。

## v1.4.12 的 401 修复

新 Release 不能修改尚未升级的旧进程。v1.4.12 已配置失效 `GITHUB_TOKEN` 时，管理员应先做以下兼容修复，再检查新版本：

1. 编辑原有环境文件，公开仓库更新可设 `GITHUB_TOKEN=`；如果私有仓库监控仍依赖 Token，应更换为权限适当且有效的 Token。保留数据库地址、`SECRET_KEY` 和其它既有配置，不重新生成配置文件。
2. 原生部署执行 `sudo systemctl restart qbot`，让旧进程重新读取 `/etc/qbot/qbot.env`。
3. Docker 部署需要重建 backend 容器以重新读取 `env_file`，单纯 `docker compose restart` 不会更新容器环境。使用自定义环境文件时同时传给 Compose 插值与服务：

   ```bash
   QBOT_ENV_FILE=/绝对路径/qbot.env docker compose --env-file /绝对路径/qbot.env config --quiet
   QBOT_ENV_FILE=/绝对路径/qbot.env docker compose --env-file /绝对路径/qbot.env up -d --force-recreate backend
   ```

4. 重新登录管理台，在“系统设置 → 在线更新”手动检查。旧页面若此前已对同一候选版本点过“稍后提醒”，可直接从设置页查看，或在浏览器开发者工具中删除当前站点的 `qbot_deferred_update` 键。不要清除全站凭据或数据库。
5. 按原生升级服务或 Docker 部署说明升级，刷新页面后启用本版本的有期限提醒逻辑。

匿名请求受 `403/429` 限流、服务器离线或管理员主动关闭检查时，发布新包也不能保证旧用户立即收到提示。应先恢复更新源访问或由管理员执行校验后的手动升级。

## 原生部署的自定义插件迁移

版本内置插件继续来自 `PLUGIN_DIR`；自定义代码使用持久目录 `PLUGIN_EXTENSIONS_DIR`，未配置时为 `DATA_DIR/plugins`。文档标准布局使用 `/var/lib/qbot/plugins`。插件配置、启用状态和账号绑定仍保留在原数据库中，迁移代码不会重新生成这些设置。

有自定义插件的原生部署，建议在切换 `current` 前，从已校验本次 Release 的完整源码包或 ZIP 上传包根目录重新执行新版安装器：

```bash
sudo python3 scripts/updater/install.py
```

安装器只读取并校验清单，不导入插件代码；将当前版本目录下的自定义插件复制到持久目录，保留源文件，并保留持久目录内已存在的有效副本。清单标识、权限和文件树无效时中止；不接受符号链接或特殊文件，也不允许持久路径位于 `/opt/qbot/releases`。只有已知内置标识 `dice`、`keyword_reply` 且清单明确为内置时留在版本目录。迁移前仍须另行备份数据库、环境配置、密钥及自定义插件文件。

旧升级服务不会执行新安装器。针对旧数据库中保存的 `/opt/qbot/current/backend/plugins/<id>` 路径，新运行时在当前目录已缺失时，会从保留的历史发布目录查找该**已登记**插件，核对清单标识和登记版本后迁移；不会发现或自动启用其它历史插件。如果旧源码已删除、目录布局不符或清单不能核对，加载失败会保留诊断，需要管理员从可信备份恢复代码。保留旧发布目录不能替代插件独立备份。

网页使用的 `native.tar.gz` 仅包含应用和已构建前端，不包含或替换宿主机升级服务；其 `maintenance_protocol` 仍为 `1`。完整源码包和 ZIP 上传包包含 `install.py`、`plugin_storage.py`、`daemon.py`、`build_environment.py`，供管理员按 [原生部署说明](NATIVE_SERVER.md#安装网页一键升级) 显式安装宿主机升级服务。不要只复制 `install.py` 单文件执行。

## 验证与回退

新增后端行为测试覆盖并发合并、缓存独立性、ETag/304、两类限流与时间头、失败缓存标记、取消单个等待者、匿名重试、重定向拒绝、稳定通道、无效 SemVer、离线恢复、旧 API 字段和过期结果禁止安装。前端组件与定时器测试覆盖提醒迁移、跨标签、到期、重新读取、更高版本、关闭检查、存储故障和 viewer 不提供安装操作。

对 `ef564a6` 原检查器实测：12 个并发页面发出 12 次上游请求，且接受无效预发布段 `1.2.3-01`；修复后的行为测试分别要求 1 次请求和拒绝该版本。

原生更新继续保留摘要、GitHub 来源证明、下载/解包上限、串行任务、维护闸门、升级前备份和启动失败回滚。已有自测覆盖不可信资产、重定向、镜像损坏、并发安装、数据恢复和恢复写入后的回滚边界。本轮没有放宽这些校验。维护闸门移除、应用恢复写入后，不自动覆盖新写入的数据；此后故障进入人工检查状态。真实 Linux/systemd 安装、生产 QQ/AI 和真实跨主机网络场景须单独记录，不把 Mock 或源码探测作为这些场景的通过证明。
